API 2.2 builds on [API 2.1](v2.1.md) with a handful of additions, mostly to presets. If you use TypeScript, check the [value feedback typings change](#typescript-value-feedback-schemas-declare-their-result-type) when updating. Also check that your variable ids are [valid](#variable-id-validation), and whether you use any [deprecated regexes](#regex-deprecations).

## TypeScript: value feedback schemas declare their result type

When strongly typing your feedbacks, a `value` feedback's schema must now include a `result` property, describing the type its callback returns. The callback is then type-checked against it.

Before:

```ts
type FeedbacksSchema = {
  channel_level: {
    type: 'value'
    options: {
      channel: number
    }
  }
}
```

After:

```ts
type FeedbacksSchema = {
  channel_level: {
    type: 'value'
    options: {
      channel: number
    }
    result: number | null // now required for value feedbacks
  }
}
```

```ts
const feedbacks: CompanionFeedbackDefinitions<FeedbacksSchema> = {
  channel_level: {
    type: 'value',
    name: 'Channel level',
    options: [{ id: 'channel', type: 'number', label: 'Channel', default: 1, min: 1, max: 64 }],
    callback: (feedback) => myDevice.getLevel(feedback.options.channel), // must return number | null
  },
}
```

If you don't want to narrow the type, use `result: JsonValue`.

This is a TypeScript-only change. It has no runtime impact, and `boolean` and `advanced` feedback schemas are unchanged. It mirrors the `result` property that [actions gained in API 2.1](v2.1.md#action-callbacks-can-return-a-result-value).

## Presets: store action results in local variables

Actions which [return a result](../connection-basics/actions.md#returning-a-result) can now have that result stored into one of the button's local variables, directly from a preset. Add a `storeResult` to the action entry, naming a `simple` local variable declared on the same preset:

```ts
presets['show_level'] = {
  type: 'simple',
  name: 'Show level',
  style: {
    text: 'Level\n$(local:level)',
    size: 'auto',
    color: 0xffffff,
    bgcolor: 0x000000,
  },
  steps: [
    {
      down: [
        {
          actionId: 'read_current_value', // an action with `hasResult: true`
          options: { channel: 1 },
          storeResult: { type: 'local-variable', variableName: 'level' },
        },
      ],
      up: [],
    },
  ],
  feedbacks: [],
  localVariables: [
    {
      variableType: 'simple',
      variableName: 'level',
      startupValue: '',
    },
  ],
}
```

This works in `simple` and `layered` presets. When typing your presets with your module's types, `storeResult` is only accepted on actions whose schema declares a `result`.

## Presets: notes

Presets can now define `notes`, which are copied to the button when the user places the preset. Use this to describe the purpose of the button, or to give the user any setup information they need:

```ts
presets['route_output'] = {
  type: 'simple',
  name: 'Input X to Output Y',
  notes: 'Change the `input` and `output` local variables to choose the route.',
  // ...
}
```

`notes` is available on both `simple` and `layered` presets.

## Colours as CSS strings

Everywhere a module provides a colour, it can now use a CSS colour string instead of a packed RGB number. For example, `'#ff0000'` and `'rgb(255, 0, 0)'` are both equivalent to `0xff0000`.

This applies to:

- the `color` and `bgcolor` style properties, in simple presets, boolean feedback `defaultStyle`, boolean feedback styles in presets, and the values returned by advanced feedbacks
- the colour properties of [graphics elements](../connection-basics/graphics-elements.md) (`color`, `outlineColor`, `borderColor`, `markerColor`, and the `color` of gauge stops)

```ts
style: {
  text: 'Stop',
  size: 'auto',
  color: '#000000',
  bgcolor: 'rgb(255, 0, 0)',
},
```

Packed numbers (`0xff0000` or `combineRgb(255, 0, 0)`) continue to work, and you can mix both forms freely. The new `CompanionColorValue` type (`number | string`) describes either form.

## Variable id validation

Variable ids must only contain letters, numbers, `-`, `_`, `.` and `!`. Since Companion 5.1, any definition with an invalid id, or with a reserved id such as `constructor`, is ignored and a warning is logged. This applies to modules using any 2.x API version. Previously, a reserved id caused an error.

If you set `disableVariableValidation`, values for undefined variables with invalid ids are now dropped with a warning. Modules using an older API version are only warned, and the value is still set.

The new `sanitizeVariable` helper turns a string, such as a channel name reported by the device, into a valid id. See [invalid variable ids](../connection-basics/variables.md#invalid-variable-ids).

## Regex deprecations

Many of the `Regex` patterns are better handled by another field type, so they are now deprecated and log a warning when used:

| Deprecated                                                         | Use instead                                                                      |
| ------------------------------------------------------------------ | -------------------------------------------------------------------------------- |
| `IP`                                                               | A `textinput` without a regex, so that hostnames and IPv6 can be used, or `IPV4` |
| `HOSTNAME`                                                         | A `textinput` without a regex                                                    |
| `PORT`                                                             | A `number` field with `min: 1` and `max: 65535`                                  |
| `PERCENT`                                                          | A `number` field with `min: 0` and `max: 100`                                    |
| `NUMBER`, `SIGNED_NUMBER`, `FLOAT`, `SIGNED_FLOAT`, `FLOAT_OR_INT` | A `number` field                                                                 |
| `BOOLEAN`                                                          | A `checkbox` field                                                               |
| `SOMETHING`                                                        | `minLength: 1` on the `textinput`                                                |

The new `Regex.IPV4` and `Regex.IPV6` patterns are available for devices which require that kind of address. Using a `Regex` key that doesn't exist also logs a warning. See [validating text inputs](../connection-basics/input-field-types.md#validating-text-inputs).

## UDPHelper: IPv6 support

`UDPHelper` now uses a `udp6` socket when the host is an IPv6 address, and has a new `family` option to choose it manually. Log messages from the helpers now wrap IPv6 addresses in brackets. See [UDPHelper](../connection-basics/connecting.md#udphelper-class).

## Graphics: rotation on composite elements

A [composite element](../connection-basics/graphics-elements.md#composite) can now be given a `rotation`. The range of `rotation` on all elements is now documented as -360 to 360 degrees, matching Companion's own rotation property.
